## How it was written

The general method is in [../METHOD.md](../METHOD.md): which controls are chosen, how a control is matched to scanner findings or left to a person, and what the severity floors and evidence windows mean. For this framework:

- A complement, not a duplicate: the built-in framework reads requirement 6 by scan category with a 30-day window and no severity floor. A second framework that read the same requirements differently would give two answers for one control, so the overlapping ones are left to it.
- Scanning and testing requirements (11.3.1) read recent scans plus open high or critical findings. External scans by an Approved Scanning Vendor (11.3.2) and penetration tests (11.4.x) are done by named parties, so they are manual.
- 2.2.1, 3.5.1 and 4.2.1 name a property rather than a weakness. They use the weakness classes that break the property (METHOD.md); PCI DSS itself maps none.
- Evidence window: **90 days.** Requirement 11.3.1 asks for internal vulnerability scans at least once every three months, so a scan within 90 days is evidence.
- 13 controls: 4 matched to scanner findings, 9 manual.

## What it does not cover

- Requirements about cardholder data environments, network segmentation, access control, logging and physical security are not listed: they are not software findings.

## How to read the result

A matched control reads `clear` when a scan that could evidence it ran within the window and nothing it counts is open, `open` when something is open, and `not assessed` when no such scan ran. A manual control stays unassessed until a person attests it. A `clear` control means *no open finding of the kind the control watches*; it does not prove the requirement is met.
